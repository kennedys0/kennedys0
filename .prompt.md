Allow visitors to solve deliberately designed Web and API security challenges in safe, authorized training environments.

## Arena Features

Design an interface supporting:

- Challenge catalog
- Web / API categories
- Difficulty filters
- Challenge descriptions
- Rules and hints
- Flag submission
- Attempt feedback
- Completion status
- Optional progress tracking
- An optional verified leaderboard

Possible challenge types:

- HTTP response analysis
- Access control reasoning
- JWT security concepts
- API authorization analysis
- Broken object authorization in synthetic examples
- Rate limiting logic
- Request validation
- Business logic reasoning

## Safety Architecture

Never deliberately weaken the portfolio's production application to create a playable security challenge.

Use one of two implementations.

### Mode A — Safe Interactive Training

Default MVP.

Build educational exercises based on synthetic HTTP requests, responses, mock data, and validated answers.

No vulnerable live endpoint is required.

Answers are checked server-side.

The browser must not contain hidden flags or answer keys.

### Mode B — Isolated Hands-On Labs

Future extension.

Only implement if a safe infrastructure environment is available.

Hands-on labs require:

- Separate disposable environments
- Isolation from production
- No production database access
- No access to production credentials
- Strict network egress controls
- Resource limits
- Container or VM lifecycle controls
- Session expiration
- Abuse monitoring
- Automated cleanup
- Per-session challenge secrets
- No privileged containers
- No access to the host container runtime

Do not claim labs are isolated unless isolation is implemented and tested.

Do not allow users to attack the main portfolio domain as part of a challenge.

If secure lab infrastructure is unavailable, implement Mode A completely and document Mode B as a future extension.

## Arena Experience

Create a refined challenge workspace with:

- Challenge description
- Synthetic HTTP request viewer
- Synthetic response viewer
- Answer input
- Hint panel
- Submission feedback
- Explanation after completion

The experience should feel like a purpose-built security training interface.

Avoid making the entire website look like a terminal.

# 10. SECURITY REQUIREMENTS

This is a security researcher's website.

Its own security must be taken seriously.

Implement and verify:

- Server-side input validation
- Authentication security
- Authorization checks on every private operation
- Secure session management
- CSRF defenses where applicable
- Context-appropriate output encoding
- Safe error handling
- Rate limiting
- Spam and abuse protection
- Security-conscious HTTP headers
- Secret management
- Safe database access
- Controlled logging
- Dependency security checks
- Least-privilege access
- Sensitive data protection
- Abuse-resistant challenge submissions

Never trust client-controlled status fields, admin flags, or ownership assertions.

For user-submitted links, protect against SSRF by avoiding automated requests entirely in the MVP.

For user-submitted content, protect against stored XSS and unsafe rendering.

For challenge forms, consider privacy, retention, deletion procedures, consent, and appropriate anti-abuse controls.

Do not store unnecessary personal information.

Do not expose private administrative routes without working authentication.

Do not use a hardcoded admin password.

Do not leave development debug endpoints exposed in production.

Challenge workflows must never perform real-world scanning or exploitation automatically.
